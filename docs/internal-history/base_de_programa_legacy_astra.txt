SECCIÓN 1 — CATÁLOGO FUNCIONAL Y LÓGICA DE NEGOCIO
¿Qué es Astra Campaign y para quién es?
Astra Campaign es una plataforma SaaS multi-tenant de marketing y automatización por WhatsApp. Está diseñada para empresas (tenants/clientes) que necesitan enviar mensajes masivos, gestionar contactos y construir flujos de chatbot automatizados sobre WhatsApp. La plataforma es administrada por un SuperAdmin que gestiona las empresas clientes y sus cuotas.

Usuarios del sistema:

SuperAdmin: Rol global. Crea y administra empresas (tenants), gestiona configuraciones globales del sistema (proveedores WhatsApp, branding), y puede impersonar cualquier tenant mediante el header X-Tenant-Id.
ADMIN (Tenant Admin): Administrador de una empresa específica. Gestiona usuarios, configuraciones de integración, y todas las funcionalidades de su tenant.
USER: Usuario regular de un tenant. Accede a contactos, campañas y flujos según los permisos que le asigne su Admin.

Este es el panel de control central de las conexiones WhatsApp. El usuario puede:

Crear nuevas sesiones/conexiones de WhatsApp en tres proveedores distintos:
WAHA (WhatsApp HTTP API): Sesiones basadas en QR code. El sistema genera un nombre técnico único (ej: empresa_abc123) con un displayName amigable (ej: ventas).
Evolution API: Conexión vía QR en la instancia propia del Evolution container.

Escanear QR codes para vincular el número de WhatsApp.

Eliminar sesiones tanto del sistema como del proveedor externo.
Sincronizar estado — el backend consulta automáticamente la API de WAHA/Evolution/QuePasa cada vez que se carga la página para actualizar los estados.
Habilitar Campañas Interactivas para una sesión específica (toggle interactiveCampaignEnabled).
Configurar Webhook — cada sesión tiene un webhookSecret único generado con crypto.randomBytes(32). La URL de webhook es POST /api/webhooks/incoming/:sessionId/:webhookSecret.
Regla de Multi-Proveedor: El sistema soporta múltiples proveedores simultáneamente. Una campaña puede tener múltiples sesiones de distintos proveedores y el scheduler las distribuye en round-robin sequencial.

Arquitectura Multi-Tenancy — Aislamiento de Datos
El aislamiento se implementa en tres niveles:

Nivel 1: JWT Token
Cuando un usuario hace login, el backend genera un JWT que contiene { userId, email, role, tenantId }. El tenantId queda codificado en el token — el usuario no puede cambiarlo.

Nivel 2: Auth Middleware (backend/src/middleware/auth.ts)
En cada request autenticado:

Extrae y verifica el JWT (jwt.verify con JWT_SECRET).
Busca el usuario en BD y verifica que esté activo (ativo: true).
Excepción SuperAdmin: Si el rol es SUPERADMIN, puede sobreescribir el tenantId enviando el header X-Tenant-Id. Esto permite a SuperAdmin "impersonar" cualquier tenant para gestión.
Si el usuario tiene tenantId, busca el tenant en BD y verifica que esté activo (active: true). Si el tenant está inactivo, devuelve 401.
Adjunta req.user, req.tenantId y req.tenant a la request para uso en controllers.
Nivel 3: Filtrado en cada Query de BD
Todos los controllers y servicios filtran por tenantId en cada consulta Prisma. Por ejemplo:

typescript

// contactController.ts
const contacts = await prisma.contact.findMany({
  where: { tenantId: req.tenantId } // ← Siempre filtrado
});
Esta no es una Row-Level Security a nivel de BD, sino una convención de código — cada controller recibe el tenantId del middleware y lo aplica explícitamente en cada query.

Nivel 4: Quota Middleware (backend/src/middleware/quotaMiddleware.ts)
Antes de crear nuevas conexiones, el middleware checkConnectionQuota verifica que el tenant no haya superado su maxConnections. Si se supera la cuota, se genera una alerta automática.

SECCIÓN 5 — REGLAS DE ORO Y PREVENCIÓN DE DESASTRES
Regla 1: Prevención de Bucles Infinitos en Webhooks (isFromMe)
Problema: Cuando el sistema envía un mensaje vía WhatsApp, el proveedor (Evolution/WAHA/QuePasa) puede devolver un evento webhook notificando ese mismo mensaje enviado. Si el sistema lo procesa, podría generar una respuesta, que genera otro webhook, creando un bucle infinito.

Solución implementada en 
incomingWebhookRoutes.ts
, línea 75:

typescript

// Processar mensagem para campanhas interativas
// Ignorar mensagens enviadas pelo bot (isFromMe = true)
if (messageData.isFromMe) {
  console.log(`⏭️ Ignorando mensagem enviada pelo bot`);
  return res.status(200).json({
    success: true,
    message: 'Message from bot ignored',
  });
}
Cómo se detecta isFromMe por proveedor:

Proveedor	Campo en Payload	Valor
Evolution API	payload.data.key.fromMe	true
WAHA	payload.payload.fromMe	true
QuePasa	payload.fromme === true OR payload.frominternal === true	true
Punto crítico: La función extractEvolutionMessage() solo procesa payloads con event === 'messages.upsert'. Para WAHA, solo procesa event === 'message.any'. Cualquier otro evento es ignorado devolviendo null, lo que también devuelve HTTP 200 con message: 'Message ignored' — evitando reintentos del proveedor.

Regla 2: Failsafe HTTP 200 — Nunca Colapsar la API Proveedora
Problema: Si el servidor responde con HTTP 5xx a un webhook de Evolution/WAHA/QuePasa, el proveedor reintentará el webhook múltiples veces, potencialmente ejecutando el mismo mensaje varias veces o sobrecargando el servidor.

Solución implementada en 
incomingWebhookRoutes.ts
, líneas 100-108:

typescript

} catch (flowError: any) {
  console.error(`❌ Error processing flow:`, flowError);
  // Retornar 200 mesmo com erro para não fazer o provider reenviar
  res.status(200).json({
    success: true,
    message: 'Webhook received but flow processing failed',
    error: flowError.message,
  });
}
La regla es: El webhook siempre responde HTTP 200 aunque el procesamiento del flujo interno falle. Esto garantiza que el proveedor considere el webhook como "entregado exitosamente" y no lo reintente. Los errores se loguean internamente pero no se propagan como errores HTTP.

Excepción deliberada: Si la sesión no se encuentra en la BD (session not found), el sistema SÍ devuelve HTTP 404 — porque ese webhook no es para esta instancia y el proveedor debería saber que fue un error de configuración.

Regla 3: Prevención de Mensajes Duplicados en Campañas
Problema: El scheduler corre cada 30 segundos y podría procesar la misma CampaignMessage dos veces en paralelo si hay race conditions.

Solución triple implementada en 
campaignSchedulerService.ts
:

Nivel 1 — Marcado atómico como PROCESSING (líneas 208-213):

typescript

// IMMEDIATELY mark message as PROCESSING to prevent duplicate processing
await prisma.campaignMessage.update({
  where: { id: message.id },
  data: { status: 'PROCESSING' }
});
El scheduler solo busca mensajes en estado PENDING (no PROCESSING). Al marcarlo inmediatamente, otras instancias del scheduler no lo tomarán.

Nivel 2 — Verificación de contacto ya procesado (líneas 267-291):

typescript

const alreadyProcessed = await prisma.campaignMessage.findFirst({
  where: {
    campaignId: campaign.id,
    contactId: message.contactId,
    status: 'SENT'
  }
});
if (alreadyProcessed) {
  // Marcar como FAILED con mensaje explicativo y saltar
}
Nivel 3 — take: 1 en la query de mensajes (línea 91):

typescript

messages: {
  where: { status: 'PENDING' },
  orderBy: { criadoEm: 'asc' },
  take: 1 // Processar uma mensagem por vez
}
Solo se procesa 1 mensaje por campaña por ciclo del scheduler, garantizando serialización natural.

Regla 4: Solución de CORS — Proxy Server-Side
Problema: Las herramientas de testing de conectividad del frontend (verificar URL de WAHA, Evolution, Chatwoot, Perfex) hacen fetch directamente desde el browser, generando errores CORS cuando los servidores destino no tienen los headers CORS apropiados.

Solución implementada en 
httpProxyRoutes.ts
:

typescript

// POST /api/http-proxy/test
// El frontend envía: { url, method, headers, body, timeout }
// El backend hace el fetch server-side (sin CORS) y devuelve la respuesta
El backend actúa como proxy HTTP: el frontend envía la solicitud al backend (que sí tiene CORS configurado), y el backend hace el fetch() real al servicio externo sin restricciones CORS. Se incluye un AbortController con timeout configurable (default 30s).

Regla 5: CORS Configuración Dinámica (Lista Blanca)
Archivo: 
server.ts
, líneas 58-77.

typescript

const corsOptions = {
  origin: function (origin, callback) {
    const allowedOrigins = process.env.ALLOWED_ORIGINS?.split(',') || [
      'http://localhost:3000',
      'http://localhost:5173',
    ];
    // Permitir requests sin origin (mobile apps, scripts, etc.)
    if (!origin) return callback(null, true);
    if (allowedOrigins.indexOf(origin) !== -1) {
      callback(null, true);
    } else {
      callback(new Error('Não permitido pelo CORS'), false);
    }
  },
  credentials: true,
  optionsSuccessStatus: 200
};
Puntos críticos:

Los orígenes permitidos se leen de ALLOWED_ORIGINS en .env (separados por coma), por lo que el whitelisting es configurable sin recompilar.
Requests sin Origin header (mobile apps, scripts internos, cURL) son siempre permitidos — esto es necesario para que los webhooks de los proveedores funcionen.
WebSocket (Socket.IO) también tiene su propia configuración CORS replicada en websocketService.ts usando la misma variable de entorno.

Regla 7: Validación de Número WhatsApp Antes de Enviar
Antes de cada envío en campaña masiva, el scheduler verifica que el número existe en WhatsApp mediante el método checkContactExists() del proveedor correspondiente. Si el número no existe:

La CampaignMessage se marca como FAILED con errorMessage: "Número não existe no WhatsApp (PROVIDER)".
Se incrementa failedCount en la campaña.
No se consume quota del proveedor de mensajería.
Regla 8: Unicidad de Sesión por Contacto en Flujos Interactivos
El modelo InteractiveCampaignSession tiene una restricción UNIQUE([campaignId, contactId]) — un contacto no puede tener dos sesiones activas en la misma campaña. Si el mismo número escribe de nuevo, el FlowEngine reutiliza la sesión existente y continúa desde el nodo donde quedó.

Regla 9: Webhook Secret para Seguridad de Webhooks
Cada sesión de WhatsApp tiene un webhookSecret único generado con crypto.randomBytes(32).toString('hex'). La URL del webhook tiene el formato:


POST /api/webhooks/incoming/{sessionId}/{webhookSecret}
La validación del secret está actualmente comentada para facilitar el debug, pero la arquitectura está preparada para activarla. Cuando se activa, si el webhookSecret en la URL no coincide con el almacenado en BD, devuelve HTTP 401.

Regla 10: SuperAdmin Impersonation via Header
El SuperAdmin puede gestionar datos de cualquier tenant enviando el header X-Tenant-Id: {tenantId} en sus requests. El authMiddleware detecta el rol SUPERADMIN y reemplaza el tenantId del JWT con el del header:

typescript

if (user.role === 'SUPERADMIN') {
  const headerTenantId = req.header('X-Tenant-Id');
  if (headerTenantId) {
    effectiveTenantId = headerTenantId;
  }
}
Esto permite al SuperAdmin crear/gestionar recursos en nombre de cualquier tenant desde el panel de administración.
